## 二、为什么「外观先做、接缝后做」反而是正确的顺序

不是抢活，是依赖关系决定的：

1. 碰撞体（`obstacles.push`）和展品热点（`registerSpot`）的坐标**全部来自外观几何的最终位置**——墙在哪、门多宽、展台多高、挂画多高。
2. 外观没定稿就先登记接缝，等于按一个假尺寸做 15 处坐标，外观一改全部作废，还会连带组员2（碰撞）、组员4（拾取）、组员7（路由传送）返工。
3. 所以顺序是：**外观定稿 → 接缝登记一次到位 → 下游三人的验收才稳**。

这条理由可以直接写进答辩：*"模块依赖决定开发顺序，我们先冻结外观几何坐标，再登记碰撞与热点，避免跨模块返工。"*

## 五、同一个文件不打架的三条规则

1. **时间上串行**：第一周组长独占 `scene.js` 打样到定稿；组员1 这一周做准备（列出 35 个碰撞体与 10 个热点的目标数值表、读懂 `player.js` 怎么用 `obstacles`、跑一遍现有场景记录问题清单）。
2. **定稿信号**：组长 PR 里写明外观坐标定稿版本；她从那之后再动 `obstacles` / `registerSpot` / `hallRegions`。
3. **提交习惯**：每次动手前 `git pull --rebase origin main`；真出现冲突，由**后动手的人**（她）解。

> 真到了必须并行的那天，再考虑把登记类代码挪到独立文件 `js/scene-registry.js`——那是结构改动，要改 `index.html` 引入并全组回归，非必要不做。

## 六、合并前自查（组长跑，10 分钟）

1. `npm run dev`，三个入口 `#/hall/plaza`、`#/hall/hall1`、`#/hall/hall2` 都能进、落点在地面。
2. 键盘 W 从出生点直行进门，一路不被卡；沿西侧能走进连廊。
3. 每件展品前顶栏出现「可查看」，按 E 弹的是正对那件。
4. 顶栏展厅标签随位置正确切换。
5. 室内外明暗有层次，展品有重点照明，无死黑、无过曝。
6. 性能面板 ≥40fps。
7. `git log --stat` 确认改动只落在 `js/scene.js`（+ 必要文档）。
