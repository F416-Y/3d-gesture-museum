## 二、模块依赖与约定（避免冲突的关键）

```
config.js ──→ scene.js ──→ player.js ──→ main.js
     └──────→ exhibit.js ─┘      ↑
                         gesture.js
ui.js ←—— exhibit.js / main.js
```

**铁律：**
1. 每人只改自己负责的文件；需要改别人的文件时，提 PR 由对方 review。
   **例外：`js/scene.js` 为组长（外观）与组员1（接缝）共管**——
   - 同一时刻只有一人在改：动手前在群里说一声，改完再说一声；
   - 接缝依赖的坐标已冻结 v1（见 [任务依赖图](./任务依赖图.md) 第八节），组员1 可直接按 v1 登记；组长后续的视觉打磨（材质/灯光/装饰）不改这些坐标，若确需改动，组长提前在群里公告受影响登记点；
   - 该文件一律**交叉 review**：组长改 → 组员1 review，组员1 改 → 组长 review；
   - 冲突由**后动手的人**解决（先 `git pull --rebase origin main`）。
2. 所有模块挂在 `window.MuseumXxx` 命名空间下，通过「只读导出、不写他人状态」解耦。
3. `config.js` 是唯一数据源：新增展品只改 config，不改 scene（除挂载坐标）。
4. **每个子任务新开一条分支** `feature/<模块>-<子任务>-<组员序号>`（如 `feature/scene-collision-1`），完成后提 PR；PR 合并后立刻删掉该分支。完整清单见 [组员上手指南](./组员上手指南.md) 2.3 节。

## 三、Git 协作流程（GitHub）

```
main（★ 默认分支 · 唯一主线 · 稳定版，禁止直接 push；PR 必须经组长批准才能合并）
  └── feature/<模块>-<子任务>-<组员序号>    一个子任务一条，合完即删
        例：feature/scene-collision-1    （组员1 · 碰撞体登记）
            feature/player-collision-2   （组员2 · 碰撞检测）
            feature/scene-look-7         （组长 · 场景外观）
        完整清单见 [组员上手指南](./组员上手指南.md) 2.3 节
```

**操作手册**：每个组员的日常 Git 命令（首次 clone、每日流程、冲突处理、素材大小约定）见 [Git-快速上手.md](./Git-快速上手.md)。

每日流程：
1. 开工前 `git switch main && git pull origin main` 同步最新代码。
2. 在个人分支开发，`git commit` 写清改动。
3. 完成一个功能 → 提 PR 到 `main`（base 默认就是 main）→ 组长 review 后才会合并。
4. `main` 必须随时可演示：组长每次合并 PR 前先在本地跑一遍；里程碑与答辩前打 tag 冻结（如 `v0.1-week1`、`v1.0-demo`），Pages 从 `main` 自动更新。

**所有人都走分支**：先在 `feature/*` 上开发，再提 PR 合入 `main`——**组长也一样**。合并这道关只认组长的 review：`.github/CODEOWNERS` 把整个仓库指给组长，配合 `main` 的分支保护（Require a pull request + Require review from Code Owners），别人的 PR 没有组长批准合不进来。

`main` 是**仓库默认分支**，也是唯一主线，必须**随时可演示**：任何人禁止直推（`.githooks/pre-push` 拦本地，GitHub 分支保护拦网页）；里程碑和答辩前由组长打 tag 冻结演示版。

场景外观因为要和组员1 的接缝错开，组长用独立分支 `feature/scene-look-7`；同文件 `js/scene.js` 的冲突在 PR 合并到 `main` 时解决。

仓库配置（组长操作）：
- Settings → Pages：部署分支 `main` / `docs` 或 GitHub Actions。
- 素材入库前启用 Git LFS：`git lfs track "assets/images/*" "assets/models/*"`。
- `.gitignore` 已配置，避免 node_modules、临时文件、大素材误提交。

## 五、美术鉴赏作业要点（评委可能问）

1. **为什么做数字博物馆**：美术鉴赏强调「观看方式」，3D 空间重建了美术馆的观看情境——走近、仰视、灯光下的原作氛围，这是图册无法替代的。
2. **美术维度**：新中式建筑美学（对称、飞檐、朱柱、匾额）；展厅叙事动线（前庭—绘画—器物—中西对话）；灯光模拟展陈照明。
3. **软件工程维度**：模块化解耦（7 模块全局命名空间）、Git 分支协作、碰撞检测、状态机（手势识别）、降级设计（摄像头失败→键盘）。
4. **创新点**：手势隔空交互（MediaPipe）替代键鼠，体现「人机交互」前沿方向。
5. **诚实说明**：名画与雕塑为示意素材/简化模型，替换方式已在 README 说明——展示真实素材替换效果更佳。
